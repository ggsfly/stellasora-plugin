## 二、数据链路：抓取

### 2.1 接口（全部实测）

基址 `https://www.gamekee.com`，请求头必须带：

```python
{
    "game-alias": "stellasora",
    "Lang": "zh-cn",
    "X-Requested-With": "XMLHttpRequest",
    "User-Agent": "Mozilla/5.0",
}
```

| 接口 | 用途 | 实测 |
|---|---|---|
| `GET /v1/entry/treesByPidV1` | 按目录记录 `content_id` 与归属，不单靠目录定覆盖 | 本轮 627 个唯一 `content_id` |
| `GET /v1/content/pageList?page_no=N&limit=100` | 文章清单，`page_total = ceil(total/limit)` | 8 页 / 745 篇 |
| `GET /v1/content/detail/{id}` | 单篇详情，`data.content_json` 解码后为节点数组或带 `pages` 的对象 | 本轮 722/722 详情落盘，两种结构见 3.1 |

**分页参数是 `page_no`，不是 `page`**（实测 `page=2` 返回第 1 页）。

### 2.2 归属与排除

```
抓取清单 = 全部 detail（type ∈ {2, 4}）− how_owned（六属性页）
```

`how_owned` 由现有 `gamekee.ELEMENT_PAGES`（`tools/gamekee.py`）派生，**不是新常量**：

```
water=714580  fire=715868  light=715966
dark=715957   wind=715960  earth=715965
```

这六页在 `pageList` 里（标题为「水系阵容推荐」等）但**不在目录树**，是 how 正在消费的一图流攻略页，what 不重复抓、不重复发。

**按真实 `pageList` 的 ID / `type` 归并**：普查以 `pageList` 返回的 **`pageList.id`（归一为 `content_id`）** 与 `type` 为准逐条落清单，**不以标题或目录树位置反推**。`type ∈ {2, 4}` 是抓取口径，其余类型登记为排除并留原因。

**不硬编码篇数**。运行时按实际清单计算，日志输出 `总清单 N / 排除 how_owned M / 待抓 K`。本轮快照实测见 13.2.1；下一轮仍按实际清单计算。

### 2.3 节奏与失败

- 同一 GameKee API 主机：**最多 1 条在飞请求，串行；请求间隔沿用 0.12 秒**（实测依据见 8.1）
- socket 超时 20s；树/列表响应上限 4 MiB，详情 1 MiB
- 超时、5xx：最多重试 2 次，间隔 4s、12s
- 429：**尊重 `Retry-After`**；无该头则至少冷却 30 分钟并暂停整个队列
- 401/403、验证页、外层契约漂移：**立即停批**，记录端点与原因

**关于间隔的纪律**：0.12 秒来自一次 744 篇连续抓取零失败的实测，**不是 GameKee 公布的配额，也不构成「反复全量抓取永远安全」的保证**。一旦观察到 429、验证页或连续 5xx，按上面的失败纪律停批并记录，**不自动增大间隔后悄悄重试**——降速是运维决策，不是代码里的隐形兜底。

**失败纪律**（本项目禁止兜底掩盖）：

- 整批不发布：清单校验失败、预期关键结构变形、原文/库提交失败
- 允许记录并继续：策略排除的文章（`excluded`）、确认非关键的节点（`partial_parse`）
- 真正无可提取文字的页面标 `media_only`，**这是合法状态，不是错误**（判定方法见 3.3）
- 日志保留端点、ID、节点路径、异常原因；**失败绝不改报「未收录」**

**研究阶段（第十三章阶段 1）额外要求——三份必须留存的差异清单**：

| 清单 | 内容 |
|---|---|
| 树/列表差异 | 目录树有而 `pageList` 无、`pageList` 有而目录树无的条目，逐条留 `pageList.id`（归一 `content_id`）与判定 |
| 缺页 / 取不到 | 清单里有但详情 404 / 空 `content_json` / 结构异常，逐条留 ID、HTTP 状态、原因 |
| 失败明细 | 超时、5xx、429、验证页的端点与轮次，**重试成功也要留痕**，便于回看节奏是否被上游降级 |

这三份清单是后续「全量结构可分析 vs 仍需判定图像语义」的分界证据（见 13.2）。**清单只落本地研究区，不进安装包。**

### 2.4 增量判定（每次 `/st_update`）

GameKee **没有 ETag / Last-Modified / Cache-Control / version**（实测确认），`updated_at` 是唯一观测信号，**不能当 CDC 用**。

每次 `/st_update` 重取完整目录 + 完整清单（这是全库校验），按 `content_id` 对账：

| 情况 | 动作 |
|---|---|
| 新 `content_id` | 抓详情 |
| `updated_at` 变化（含倒退） | 抓详情 |
| `updated_at` 缺失 | 抓详情 |
| 只有标题/分类/目录归属变化 | 更新元数据与索引，正文可复用 |
| `updated_at` 未变 | **轮换抽验**（每轮抽固定比例的等戳条目比对正文 hash） |

**等戳异文处理**：抽验发现 `updated_at` 未变但正文 hash 变了 → **本轮把详情抓齐再发布**，不偷偷降级。

hash 只确认已取回版本，**不是全库不变证明**——日志要区分「全清单已核对」和「逐篇详情已重抓」。

### 2.5 发布模型：分代原子切换

```
data_dir/what/
  current.json                  # 指针：代名 + 覆盖范围 + 各时间戳
  kb-<generation>.sqlite3       # 正式代（只读）
  staging/build.sqlite3         # 备库（唯一写者）
```

1. 备库单写，`PRAGMA journal_mode=DELETE`（**避开 SQLite 3.50.4 的 WAL-reset 缺陷**）
2. 校验通过后关闭连接，改名为唯一代际文件名
3. 在代际锁下原子替换 `current.json`（`os.replace`）
4. 读请求**整次调用固定一个已发布代**（别名表、结构化值、FTS 同代）
5. 旧代等待读者释放后回收；**绝不 unlink/rename 使用中的数据库文件**
6. **不触碰宿主数据库，不原地替换**

### 2.6 时间戳语义（分离，不混用）

| 字段 | 含义 |
|---|---|
| `last_attempt_at` | 上次尝试时间（无论成败） |
| `last_failure_at` | 上次失败完成时间 |
| `last_verified` | **所声明服务范围完整校验成功**的时间（只在整批成功后才推进） |
| `built_at` | 当前代的构建时间 |

手动维护意味着**资料可能停留在上次操作**，不因时间到了自行刷新。查询时附「资料截至 `<last_verified>`」。

## 三、数据链路：解析

### 3.1 `content_json` 的两种实测结构

`content_json` 在详情中是 JSON 字符串，解码后按顶层形状分派；不把任意对象当成空正文：

| 顶层 | 本轮篇数 | 解析与查找 |
|---|---:|---|
| 节点数组 | 680 | 遍历富文本、图鉴结构块、折叠、表格与媒体字段；按章节与实际位置索引。 |
| `__tjMeta` / `pages` 对象 | 42 | 走独立分支，保留 `pages[].data`（PC）与 `pages[].wapData`（移动）的来源；合并已证实为同一展示的重复，保留单端独有内容。`content_live_2d` 是内嵌 JSON 字符串；与 `content_bg`、`content_wap_bg` 分开登记用途及资源类型。Live2D 资源条目不自动当作 QQ 图片。 |

42 篇对象格式不是坏 JSON，`image_num` 全为零仍提取到 1,457 个媒体出现位置。初版只收数组会漏掉这整批内容（实测见 13.2.1）。这类对象的候选标题用完整清单、目录和源字段核对；空标题不凭猜测补成角色名。未知顶层结构记录为解析异常或覆盖不足，不报「未收录」。

下列节点统计来自早期快照，仅用于说明数组分支和命名差异，不作为当前数据量；本轮实测见 13.2.1。

**节点类型**（早期快照计数）：

```
paragraph 19737, table-cell 16318, image 2850, table-row 1907,
illustrated-book 1256, flod 278, table 267, link 131, header2 117,
list-item 96, audio 90, divider 59, video 58, header1 42,
popover-comment 30, image-album 21, bulleted-list 21, header3 11,
numbered-list 5, mention-doc 1
```

**`illustrated-book` 块类型**：

```
skill-info 561, tab-info 279, audio-info 156,
fight-info 148, character-profile 111, character-info 1
```

**块标题分布**（决定 `field_key` 映射）：

```
skill-info:       主位效果 106 / 辅位效果 106 / 收录语 106 / 秘纹故事 106 /
                  逸闻笔记 47 / 天赋 43 / 档案 43 / 员工手册 4
character-profile: 基础信息 68 / 基本信息 43
audio-info:       基本信息 106 / 语音 43 / 台词语音（节选）3 /
                  台词语音 3 / 台词语音（剧情配音节选）1
fight-info:       属性 148
```

**必须做的归一**（实测命名不一致）：

| 原值 | 归一为 | 数量 |
|---|---|---|
| `基础信息` / `基本信息`（character-profile） | 同一类型 | 68 + 43 |
| `薪资` / `俸禄` | `salary` | 24 + 2 |
| `audio-info` 标题为「基本信息」 | 秘纹元信息容器，**非语音** | 106 |
| `audio-info` 标题为「语音」 | 真语音 | 43 |

**`character-profile` 的 `attrList` 标签全量分布**：

```
所属 94, 生日 26, 技能 26, 地址 26, 经验 26, 武器 26, 薪资 24, 俸禄 2
```

注意：`生日` 只出现 26 次，**不等于 42 个角色都有生日**。

**`fight-info`**：早期快照里 148 页都是 `levelList = [1, 10, 20, 30, 40, 50, 60, 70, 80, 90]`（十级）。**实施时按每页实际 `levelList` 读**，不硬编码这十级——`intent.levels` 的合法值来自该页自己的列表。

**`skill-info` 条目数**：

```
收录语 1, 秘纹故事 1, 辅位效果 2(89页)/1(17页),
主位效果 3(63页)/2(26页)/1(17页), 天赋 5(43页),
员工手册 1, 逸闻笔记 3(4页)
```

→ `fact` 表必须带 `ordinal`，否则同字段多条会互相覆盖。

### 3.2 提取规则

- 递归遍历，保留标题栈、节点顺序、表格行列、`source_path`（JSON Pointer）
- 相邻富文本叶**不凭空插入空格**（中文无词边界）
- `flod` 保留 `title` 作上下文，递归其子树
- `popover-comment`：`children` 是被注释原文，`data` 是注释内容（术语表金矿，日中对照）
- `table`：按行列输出，**图片不变成伪文本**
- `list-item` / `bulleted-list` / `numbered-list`：保留层级与顺序
- `image-album` / `image` / `audio` / `video`：登记 URL、分组、顺序、标签、**出现位置**；研发阶段可选存本地原图（研究区），**安装包不打包媒体、安装后不自动下载全站媒体**
- `mention-doc`：保存可核实文本，不顺爬
- 无 `type` 的节点：按文本叶判断，**不视为未知正文块**

**媒体提取的三层区分（本条是本计划的核心修正之一）**：

| 概念 | 含义 | 是否可合并 |
|---|---|---|
| **引用位置** | 媒体在文档中的每一次出现（`source_path` + 顺序） | **不能合并**。同一张图出现在正文和立绘 Tab 是两个真实位置 |
| **唯一 URL** | 同一 `src` 的字节级去重 | 可合并用于下载 |
| **字节去重** | 不同 URL 指向同一内容（hash 相同） | 可合并用于存储 |

**只有"重复遍历同一条路径"才是双计数**，必须去重；**不同真实位置不得删除**。历史错误正是把二者混为一谈：

| 反例 | 旧结论 | 实际（精确结构） |
|---|---|---|
| `728502` | 「去重后 1」 | 深扫 **7** 个媒体引用：**6 张导航图 + 1 张横幅**。这 6 张导航图与各自对应的 `link` **分处同一个 `infoList` 项的 `content` 子树与 `title` 子树**（**不是**同段 `children` 兄弟关系）。旧「去重后 1」是**浅扫漏**，不是去重结果 |
| `705622` | 47 个图节点被双遍历成 94 | 47 是真值；独立图段里还含引导 GIF，`word_count=0` 但实际可提取正文 |
| `715315` | `image_num=204` 当作唯一图总数 | 204 是上游 `image_num`，**非唯一图总数**。**全树 `type=image` 的字典共 9 个**，其中 **7 个是带 `type` 的 `tabList` 容器**，只有 **2 个是带 `src` 的富文本图节点**；页签实际有 **67** 条引用（按扩展名样本唯一位图 70） |

**单看"有多少个 `image` 节点"会得出错的结论**：`715315` 的 9 个字典项里只有 2 个是真图节点，其余 7 个是容器；而 67 条页签引用完全不在 `image` 节点里。**带 `src` 的富文本图引用、容器和结构化媒体字段分开计数**。

**`image_num` 的上游语义**：它是上游给出的计数，**不等于唯一的可发送图数，也不等于节点图片数**（见上表）。任何以 `image_num` 为分母的结论都必须重新验证。

### 3.3 无可提取文字页面的处理（判定方法，不是字段推断）

**不能按 `word_count` 判断纯图。** 早期用 `word_count` 反推得到「119 篇纯图」，是**错误统计**；后来统计的 115 篇是 `word_count=0` 子集中未提取到文字的记录，受当时解析器覆盖影响，不是全库确认的纯图篇数。结构普查与产品的纯图语义标注分开（13.2）。

本轮口径改为**不看任何单一字段**，按证据分级判定：

| 判定 | 依据 | `availability` |
|---|---|---|
| 可提取正文 | 递归提取后存在非空文本叶（含表格单元格、图注上下文） | `ok` |
| 无可提取文字但结构完整 | 提取结果为空文本，且节点结构可枚举 | `media_only` |
| 结构异常 / 半解析 | 关键结构缺失或解析中断 | `partial_parse` |

**判定输入至少包含**：实际提取文本、节点类型分布、媒体引用清单。**`word_count` 只作旁证**，`image_num` 不作为分母。

`media_only` 页面：收录标题、图注、媒体元数据与引用位置；FTS 可搜标题与图注，**但不假装读过图**。搜到时明确区分「定位到图片页」与「图内字段已核实」。

### 3.4 攻略类文章的图片（发送前必须校验的事实）

**webp 压缩不能假定生效**（实测同一篇文章内三张图）：

| 图 | 原图 | 加 webp 参数 |
|---|---|---|
| 第 1 张 | 940.2 KB PNG | **940.2 KB PNG（未生效）** |
| 第 2 张 | 846.3 KB PNG | 64.2 KB WEBP ✅ |
| 第 3 张 | 313.8 KB PNG | 27.3 KB WEBP ✅ |

所以发送前**必须校验响应魔数**：拿到 PNG 就按 PNG 用，拿到 WEBP 按 WEBP 用，**不假定 `?eo-img.format=webp` 一定生效**。这与现有 `gamekee._validate_image` 的魔数校验同源。

**单篇体积不预设**：早期按中位数估「一篇 10-20 MB」，只说明「全量预下载原图不现实」，**不作为单篇体积结论**，也不作为发送张数上限的依据。实际体积按 6.5 的发送前测量处理。

### 3.5 确凿的抽样证据（本轮唯一可引用为事实的部分）

本轮**确凿只有 6 篇抽样结果**，其中 4 篇的结构反例如下（保留官方链接供复核）：

### 4.2 分词契约（核心，实测驱动）

```
写入与查询共用同一函数，两侧对称是硬要求：

CJK = [\u3400-\u4dbf\u4e00-\u9fff]
def seg(text):
    return "".join(f"\u0001{ch}\u0001" if CJK.match(ch) else ch for ch in text)
```

**为什么是 `U+0001` 而不是空格**：

- 两种方案的 postings 与 MATCH 结果**实测完全一致**
- 差别只在「从索引副本逆变换」时：普通空格分不清是插入的还是原文的，`U+0001` 可保留原空格
- **但展示与复核一律从 `body` 取，不从索引逆变换**，所以 `U+0001` 的价值只是契约更干净

**FTS 短语保证 token 相邻，不保证原字符相邻**（实测）：

```
查询 "水系伤害" 会命中：
  全队水系伤害提升6%      ← 真命中
  水、系伤害测试          ← 假命中
  水 系伤害测试           ← 假命中
```

→ **必须从 `body` 做原文子串复核**，剔除假命中后再截 top-k，否则假命中会挤掉真候选。

`instr(body, ?) > 0` 作为**同规模正确性/耗时基线**（实测 7ms），但**不用作运行时静默降级**。

### 4.4 媒体角色判定与三层去重

**用途不由单一信号推断。** `image_num`、像素尺寸、是否唯一 `image` 节点，三者都不足以判断一张图的用途——见 3.2 的三个反例。

**角色枚举（标注结果，不是推断结果）**：

| `role` | 含义 | 默认是否发送 |
|---|---|---|
| `body_image` | 正文图（整篇相关） | 按意图：整篇/单问相关图分别判定 |
| `inline_icon` | 有语义的小图标（属性/职业等） | 不直接发图；已核实可转成**等价文字**随结果给出 |
| `character_art` | 立绘 / 卡池图等用户指定内容 | 仅在意图明确指向媒体目录/立绘时发 |
| `card_banner` | 横幅、卡池横幅 | 按意图，默认不发 |
| `nav_decoration` | 导航、装饰、分隔 | 不发 |
| `unknown` | 未判定 | **不发**，标 `needs_review` |

**`inline_icon` 的两条纪律**：

1. 已核实可保留成**等价文字**（如「水系」图标 → 文字「水系」），不把图标当装饰丢掉
2. 若该图标是**唯一证据**（正文没有对应文字），保留其上下文位置并标 `needs_review`，不擅自补写含义

**三层去重（不同层不互相删）**：

```
引用位置（content_id + source_path + ordinal）  ← 一行一条，永不因同 URL 合并
      ↓ 同一 src
唯一 URL                                        ← 下载去重键
      ↓ 相同 SHA-256
字节去重                                        ← 存储去重键
```

- 只有「同一条路径被遍历两次」是 bug，必须去重
- 同一 URL 出现在正文与立绘 Tab 是**两个真实位置**，两条 `media_ref` 都保留
- 删除 `media_ref` 行必须给出「重复遍历」证据，不能因为「看起来一样」

**保存键**：`(文章/版本, 节点路径和顺序)` —— 因此保留父/兄弟关系、标题或表格归属、图注、媒体角色与证据/未判状态。这既是标注集的存储格式，也是回归比对单位。

### 4.5 结论性字段先于描述性匹配

字段级结构值（生日、所属、武器、等级面板、主位/辅位效果）**必须先落成结构化 `fact`**，检索时按 `(entity, field_key, qualifier, ordinal)` 精确取。

**描述题**（「那个加地系伤害的秘纹」）要求**同一条效果内**同时匹配 对象 / 属性 / 槽位 / 条件，不能用跨条目的词袋命中凑答案。**FTS 初筛结果不得直接发出**——初筛只是候选池，必须经 4.6 的原文复核与字段/条件校验。

**日期区分**：`event_valid_range`（事件有效期，如活动起止）与 `observed_at`（我方观测日期）是两列，**不合并成一个"日期"**。回答涉及时效时必须说明给的是哪一种。

### 4.6 原文复核（不可跳过）

FTS 短语保证 token 相邻、不保证原字符相邻（见 4.2），因此：

1. FTS/结构化查询得到候选
2. 对候选**从 `body` 做原文子串复核**
3. 描述题再做字段/条件同条校验
4. 复核通过的候选才进入"最终合格候选"

`instr(body, ?) > 0` 作为同规模正确性/耗时基线，**不用作运行时静默降级**。

## 五、检索链路

### 5.1 检索总流程（意图由 planner 显式传入）

**插件看不到用户原文**（宿主只注入平台/stream/群/用户，`component_query.py:543-628`），因此**不猜意图、不靠关键词命中"攻略/原图"判断该不该发**。已有 planner 在**查询前**把结构化意图传给 what：

```python
intent = {
  "mode": "field" | "article" | "media" | "catalog",
  "subject": {"name": "优叶", "kind": "traveler"},   # 对象；名称以真实证据核对
  "shape": "single" | "list" | "whole_article",       # 形态：单值/多项/整篇
  "fields": ["stat.attack"],                          # mode=field 时的字段
  "levels": [90],                                     # 只用实际存在的等级（1~90）
  "groups": ["default"],                              # mode=media 时的立绘/卡池分组
  "date_window": {"start": "...", "end": "..."}       # 需要按日期筛时
}
```

**定义纪律**：

- `levels` **只能用实际存在的等级**（`fight-info` 的 `levelList` 是 1/10/…/90，共十级；不同页面以实际 `levelList` 为准），不杜撰等级
- `groups` 只能用 `media_ref` 里真实存在的 `group_label`
- `subject.name` 只作**查询线索**；最终对象由别名表 + 真实证据确定，查不到就报"未收录/不确认"，**不硬凑**

**流程**：

```
结构化 intent（planner 传入）
   ↓
① 实体识别（前缀树，最长匹配；保留多候选）
   ↓
② 按 intent.mode 分派：
   field   → 精确查询 fact(entity_id, field_key, qualifier)（含 levels/fields 约束）
   article → FTS 检索 chunk → body 原文复核 → 合格候选
   media   → 按 groups/形态取 media_ref（角色需已判定，unknown 不发）
   catalog → 列目录/分组/语音条目（只列事实，不下载）
   ↓ 未命中或证据不足
③ FTS 兜底检索 + 原文复核（不越权把 FTS 初筛当结论）
```

**intent 缺失或矛盾时**（旧 planner、字段不在该 `kind` 下、等级不存在）：**返回明确澄清而不是替换成别的字段**（例：问 `age` 就答「该板块无年龄字段」，不改查 `birthday`）。

### 5.2 实体识别

每个已发布代生成 `alias_norm → [(entity_id, kind, canonical_name)]`。

- 查询与别名统一做 NFKC、casefold、空白规范化，**保留版本名与括号内容**（`菈露(圣夜)` 不归一成 `菈露`）
- 用标准库 `dict` 建前缀树，最长匹配扫描问句（**无需模型**；实体数量以实际库为准，不预设）
- **重叠名称优先匹配完整长名**
- **同一名称指向多个实体时保留所有候选，不按板块顺序选第一条**

**消歧规则**：

| 问句 | 处理 |
|---|---|
| 「魔王」单独出现 | 不猜，列候选请用户选 |
| 「NPC 魔王的立绘」 | 句中「NPC」限定 → 选 NPC |
| 「魔王弱点」 | **不能**因 NPC 没有弱点字段就选名字相近的怪物 |

planner 只补它从聊天能确认的指代（「那她生日呢」→ `优叶的生日`）；**插件收到无明确对象的「她」时返回澄清提示，不跨会话猜**（插件看不到对话历史）。

### 5.3 字段映射：实体类型是**约束**，不是排序权重

**意图由 planner 传入（`intent.fields`），插件不再自行从问句猜字段。** 下面两张表是**校验表**：把 planner 给的字段名落到真实 `field_key` 与限定项上，并拒绝不合法的组合。

**字段词表**（归一 planner 传入的字段名 + 供查询侧同义扩展）：

| `field_key` | 同义问法（查询侧低权扩展） |
|---|---|
| `birthday` | 生日、诞生日、出生、几月几日生、哪天生 |
| `affiliation` | 所属、阵营、哪个协会、什么组织、出身 |
| `weapon` | 武器、用什么武器、拿什么、兵器、专武 |
| `salary` | 薪资、俸禄、工资、收入、待遇 |
| `address` | 地址、住哪、在哪、据点 |
| `experience` | 经验、干了多久、资历、工作几年 |
| `skill.talent` | 天赋、命座、被动、固有、星魂 |
| `sigil.main_effect` | 主位、主效果、主位效果 |
| `sigil.sub_effect` | 辅位、副效果、辅位效果、附加效果 |
| `stat.*` | 面板、属性、生命、攻击、防御、暴击、数值 |
| `monster.weakness` | 弱点、克制 |
| `age` | 几岁、年龄、多大（**当前无数据源，见下**） |

**板块字段表**（`(kind, field_key)` 合法性 + 限定项）：

| kind | field_key | 限定 |
|---|---|---|
| traveler | `birthday` / `affiliation` / `weapon` / `salary` | — |
| traveler | `skill.talent` | 仅 `skill-info` 标题为「天赋」的块 |
| traveler | `stat.<指标>` | **必须绑定实际存在的 `level:<n>`**（1~90，取自该页 `levelList`）；`intent.levels` 未给则追问 |
| sigil | `sigil.main_effect` | 仅标题为「主位效果」的块 |
| sigil | `sigil.sub_effect` | 仅标题为「辅位效果」的块 |
| monster | `monster.weakness` | **只登记表格文字明确给出的字段**；仅图标未核实就答「原页只有图示」 |
| npc | `affiliation` / `media_ref` | 立绘只列已判定分组 |
| — | 术语 | 取 `popover-comment` 注释证据 |
| — | 找文章（`mode=article`） | 标题命中**不冒充**正文回答 |

**关键约束**：

- `age` 是"识别得出但无数据源"的字段：**明确回答该板块未标注年龄，绝不改查 `birthday`**
- `stat.*` 的等级只接受**实际存在**的等级值；planner 传了不存在的等级（如 95）→ 返回「该页只有 1/10/…/90 级」并列出可用等级
- 描述型条件（对象/属性/槽位/条件）必须在**同一条效果**内同时满足（见 4.5）

### 5.4 多意图 / 多候选

**多个明确请求**（planner 的 `intent` 可携带多项）：

- 多子句绑同一实体时，**一次取齐所有字段**（「优叶的天赋和生日」→ 两个字段）
- 子句另写实体时**不继承**上一子句实体
- **先覆盖所有明确请求的字段，再决定每个列表给多少条**
- 某字段没值只标记该项，**不吞掉另一项**
- **不保存会话分页状态**：后续追问由 planner 补成完整 `intent` 再查

**多个最终合格候选 → 一起交付（本计划的定案）**：

| 规则 | 说明 |
|---|---|
| 合格候选 = 通过原文复核 + 字段/条件校验的候选 | 未经复核的 FTS 初筛命中**不算**候选 |
| 多个合格候选**一起发** | 不取第一条、不按置信度只发一个 |
| **来源分隔** | 每个候选的节点带来源标注（`GameKee · <文章标题> · <节点/caption>`），不让用户误认为一个来源 |
| 不是"初筛命中全发" | 只发合格候选；装饰图/未判定角色 media 一律不发 |
| 上限 | **不设固定张数上限、不默认截断为前 N**；实际受 6.5 的传输体积与组织方式约束，超限时的处置见 6.5 |

**同名多证据并存**：同一名称指向多个实体时**保留所有候选并分来源列出**，不按板块顺序选第一条。若候选数过多导致无法在一个转发里讲清，**先说明有几个候选、各是什么**，由用户收窄——不静默挑一个。

### 5.5 查询侧小词表（不做通用分词）

用标准库 `dict` 做前缀树，维护：正式名、已核实别名、属性词、效果术语、字段同义问法。

- 最长匹配用于**找短语**，不替同名候选做裁决
- **保留原查询**，限制并**低权追加**已核实同义词
- 未收录词照样走原文检索，**不假装理解开放语义**
- 词表改变**不要求重做正文索引**；归一化或分隔规则改变才重建

### 5.6 额外 LLM：非默认依赖，先证明必要

**默认不用**。本插件的 manifest 目前**没有 `llm.generate` 能力声明**（`_manifest.json` 只有 `send.text / send.forward / render.html2png / chat.get_all_streams`）。若要用宿主 LLM（`ctx.llm.generate`）：

1. 必须在 manifest 声明 `llm.generate`，并说明耗时与用量影响（每次查询多一次模型调用，超时预算要与 `_TOOL_RPC_TIMEOUT_MS` 对齐）
2. **只有对照数据证明必要时才启用**：即同一标注集上，纯程序化检索的口语覆盖不足（用户用法口语化到词表与 FTS 都接不住）
3. 用途**严格限定**为两件事：
   - 口语归一（把问法映射到已有 `field_key` / 已有实体）
   - 候选**重排**（只能对**来源白名单候选**排序，不能引入新候选）
4. **引用由程序验证**：模型选出的候选必须能回指真实 `content_id` + `source_path`，验证不过即丢弃
5. **核心事实与图路径绝不由模型产出**：数值、效果文本、日期、媒体 URL 一律取自库内原文
6. **不因此引入**向量库、OCR、或默认开启的额外推理

## 六、工具与输出（单一出口：插件自己直发）

### 6.1 工具声明

planer 传入**结构化意图 + 查询词**，what 本地查找、自己组织成合并转发并直发。

```python
@Tool(
    "stellasora_what",
    description=(
        "查询星塔旅人 GameKee 客观资料：旅人生日/所属/武器/薪资/天赋/指定等级面板、"
        "秘纹主位与辅位效果、NPC 基本资料、怪物已核实的弱点、日中术语、立绘与语音目录、"
        "以及按标题查找公告与攻略文章。只查客观资料，不给配队建议；"
        "“怎么玩/配队/队伍码/一图流”用 stellasora_how。\n"
        "本工具自行把结果合并转发到聊天：命中图文时同时发出全部最终合格候选与图，"
        "全部合格内容发完才结束本轮；拿到成功结果后不要再调用 reply 复述，也不要再发同样的图。\n"
        "intent 必须按用户真实要求填写：mode 为 field/article/media/catalog；"
        "field 时给出 fields，面板类给出 levels（只用 1/10/…/90 等实际存在的等级）；"
        "media 时给出 groups；名称不确定就不要硬写，交由本工具判定未收录或列候选。"
    ),
    parameters=[
        ToolParameterInfo(name="query", param_type=ToolParamType.STRING,
            description="必填，非空。用户问题原文（保留其字段与等级说法）", required=True),
        ToolParameterInfo(name="intent", param_type=ToolParamType.OBJECT,
            description="结构化意图：mode/subject/shape/fields/levels/groups/date_window（见计划 5.1）",
            required=True),
    ],
    platforms="qq",
    visibility="visible",
    enabled=False,          # 默认关闭；Host 读 metadata.get("enabled", True)
    timeout_ms=_TOOL_RPC_TIMEOUT_MS,
)
```

**为什么不给 `query` 加"该发/不该发"的开关**：判断权在 planner（它能看聊天上下文），载体就是 `intent.mode`（`article` = 要看原文图文，`field` = 只要事实）。插件**不再自建关键词判据**。

### 6.2 正常答案的交付路径：`ctx.send.forward`

**正常答案不分路线 A / 路线 B**：

```
intent → 本地查找 → 原文复核 → 组织节点 → ctx.send.forward(nodes, stream_id) → 返回结果
```

| 要素 | 定案 |
|---|---|
| 出口 | `ctx.send.forward`（与 how `_send_guides` 同款发送体、同款 `_FORWARD_NICKNAME`） |
| 普通事实 | **同一转发的文字节点**：`【标题】` + 事实句；来源统一放在包尾 |
| 图文混排 | 文字节点 + 图片节点在同一 `nodes` 列表，顺序按证据顺序 |
| 回传 planner 重写 | **不做** |
| 走 reply | **不走** |
| 新发送工具 / 票据机制 | **不新增** |
| 精度 Hook | **不加**（不注册 `before_post_process`） |

**节点组织**：

- 每个候选（文章/字段组/媒体组）自成一段：先文字节点说明标题和可核内容，再放其图片节点
- 多候选按标题或对象分段，不混在一个节点里
- 不给图片内容做假描述；节点文字只写能核实的事实
- 图片按该候选内的**引用顺序**发送，不跨候选重排
- **每个合并转发最后一行固定为 `来源：https://www.gamekee.com/stellasora`**；分包时每包一次，来源落款也计入每包的编码预算

### 6.3 返回契约（含四种非成功状态，必须区分）

**报错可见路径已确认**：工具回执的 `error` 不等于发给用户的消息。现有 how 加载失败时用 `ctx.send.text(提示, stream_id)` 向原会话直发一条文字，同时返回真实 `success=False`。what 可沿用这个通知机制；部分发送、送达未知的通知与停轮口径仍待收口。宿主只在成功工具回执上采纳 `stop_after_execution`，提示发出不等于资料发送成功。

| 情形 | `success` | `stop_after_execution` | 处理 |
|---|---|---|---|
| **全部合格内容成功交付** | `True` | **`True`** | 宿主据此采纳停轮，不需要 planner 再 reply |
| **未命中 / 未收录** | `True` | `True` | what 直发「没查到」并结束；这不是故障 |
| **明确失败**（库不可读、上游 4xx/5xx、权限拒绝、空参） | `False` + `error` | 不设 | 用对应的故障短语提示，不报成「没查到」 |
| **部分交付**（候选部分发送成功、部分图片失败） | `True` | **`False`** | 提示「部分发出」；已发、未发及原因留在日志或工具回执；**不设停轮**，留给 planner 决定是否补话 |
| **送达未知**（`forward` 抛异常、宿主返回未发送、超时） | `False` + `error` | 不设 | 提示「送达不确定」，**不盲重发**；后续由 planner/用户决定 |

**QQ 提示文案**：直接发短语，不加解释或套话。错误码、发送明细和异常栈留在日志或工具回执。

| 情形 | QQ 提示 |
|---|---|
| 未查到指定资料 | 没查到 |
| 资料库读取失败 | 读取失败 |
| 查询成功但没有任何资料发出 | 发送失败 |
| 部分已发、后续明确未发 | 部分发出 |
| 后续是否送达不确定 | 送达不确定 |

**关键纪律**：

- **`stop_after_execution=True` 只在"用户已经完整看到结论"时设**，两种情形：①全部合格内容成功交付；②未命中，what 已自发提示并停。其余一律不设
- **`success` 与"停轮"是两个轴**：未命中是 `success=True`（查询合法完成）且停轮；部分交付是 `success=True` 但**不停轮**；明确失败与送达未知是 `success=False` 不停轮
- **未命中 ≠ 加载失败**：未命中是合法结论，加载失败是故障，**不把故障报成"没有这个资料"**
- **部分交付不设停轮**：既不能假装全成功，也不能因为缺一张就整轮判失败
- **送达未知绝不重发**：重发可能造成重复图；宁可报未知
- 不允许"失败但 `success=True`"，也不允许"成功但 `success=False`"

### 6.4 `enabled` 拦截与默认关闭

`@Tool(..., enabled=False)` 只影响组件初始状态，热切换需显式同步。本机 SDK 方法已确认；是否启用及兼容版本上的效果仍需按 12.2 验收：

| 层 | 做法 | 状态 |
|---|---|---|
| 1. 组件状态同步 | `on_load` / `on_config_update` 调 `ctx.component.enable_component` / `disable_component` | 本机 SDK 提供 `name` / `component_type` / `scope` 等参数；映射的两项能力当前 manifest 未声明。若做热切换则补声明并验收 |
| 2. planner Hook 剔除 | `_filter_planner_tools`（`plugin.py:973`）在 `enabled=False` 时剔除 `stellasora_what`，零 schema 暴露 | 已有机制可复用 |
| 3. 执行层检查 | `handle_what` 入口再判一次，防绕过 Hook 直调 | 新增 |

**注意现有代码的坑**：`on_config_update` 在 `how.source` 未变时会提前 `return`；`what.enabled` 的组件同步**必须在该提前返回之前独立处理**。

**默认关闭的含义**（三层都要成立）：

- `enabled=False` → planner 看不到工具（零 schema、零 token）
- **零网络**：不启动任何 what 抓取、不探查 GameKee
- **零后台任务**：不排任何定时器

**开关不是采集授权**：打开开关只开通查询，见 7.2。

### 6.5 发送体积与组织方式（按目标宿主版本验收）

**帧上限随宿主版本不同，不能当成固定预算**：

| 宿主版本 | `MAX_FRAME_SIZE` | 位置 | 依据 |
|---|---|---|---|
| **v1.4.8**（当前 dev/实机） | **32 MiB = 33,554,432 字节** | `src/plugin_runtime/transport/base.py:18` | commit `fd172cd01` 由 16→32 MiB |
| **v1.3.15**（manifest 兼容下界） | **16 MiB** | 同一常量 | 同文件历史版本 |

`_manifest.json` 的 `host_application` 范围是 `1.3.15`–`1.4.99`，**横跨这两类**。因此：

- 发送预算 **按目标宿主版本取**，不把 32 MiB 当所有兼容版本的固定上限
- 32 MiB 是**单帧 payload 上限**（4 字节长度头不计），不是 QQ 条数上限、不是官方配额
- 该限制**已隔离测试**：超 1 字节即在 `send_frame` 抛 `ValueError`（`base.py:44-45`）
- 沿 how 现有路线，`send.forward` 的**全部节点 + base64 图片在同一个 MsgPack request 内**，所以"节点数多"与"图大"叠加算一个帧
- **插件式网关可能第二跳也受限**（宿主→网关→QQ 的链路未在本轮核实）

**组织方式（产品口径已定，实际分包与送达仍待实机验证）**：

| 项 | 口径 |
|---|---|
| 张数上限 | **不设固定张数**；用户要求发送全部合格内容、多候选一起交付 |
| 截断为前 N 张 | **不做默认行为** |
| **base64 膨胀** | 图片进 MsgPack 前要 base64，体积约 **×1.33**，所以"原图 N MB"不等于"N MB 帧占用"；预算要按编码后大小算 |
| 超帧时的处置 | 单包容不下时按原顺序分成多个合并转发；每包以 `来源：https://www.gamekee.com/stellasora` 收尾。单张仍放不下或有发送异常时记录真实状态，不静默截断；分包送达仍待实机验证 |
| webp | 优先压缩以降低帧压力，但**不假定压缩生效**（见 3.4，需魔数校验） |
| 实测口径 | 发送前测量 `len(msgpack)`（**编码后**），与**目标宿主版本**的上限比较；两者都要记录 |

**不得写成实测结论的句子**：不要写「QQ 无限制」；不要写「某张数一定能发 / 一定不能发」。这些都需要按宿主版本分别实测后才有结论。

### 6.6 `content` 形态（供 planner 读，不再驱动发送）

`content` 仍然返回一句可读摘要，但它**不再决定发送内容**（发送已由插件完成）：

```
已转发 2 条候选（来源分隔）：
- GameKee · 星塔学习进阶篇：秘纹基础知识（正文图 11 张）
- GameKee · 各系组队一图流（正文图 7 张）
```

- 摘要里**不重复图片内容**，不写没核实的图意
- 状态写进首句：未命中 / 部分交付 / 送达未知
- **不返回原始 JSON、字段树或整篇 Wiki**

## 七、更新机制：`/st_update`

### 7.1 命令编排

**不新增 `/st_what_update`**。一个命令受理四路，内部保留两个任务句柄：

- `_update_task`：原有攻略探查 + 两榜强刷（不变）
- `_what_update_task`：资料同步（新）

两者在首次 `await` 前登记，分别单飞。`what` 在跑时不重开抓取；原三路空闲时仍可再次更新。**`what` 关闭时不创建第四路**。

**原有报告不等资料同步完成**（保持现有节奏）。若共用 GameKee 请求预算，**给短探查优先权**，不让长批独占队列。

### 7.2 建库与增量：唯一的采集入口

**采集只有这一个入口。** 打开 `[what] enabled` 只同步组件状态并检查本地已发布代，**不访问 GameKee**：

| 状态 | 返回 |
|---|---|
| 已有库 | 立即可查 |
| 没有库 | 「星塔资料查询已启用，但资料库还没建好。请让有权限的操作员执行 `/st_update`。」 |
| 建库中 | 「正在首次建库，完成后才能查询（已完成 X/Y）」 |

**四条不可越的线**：

1. **不自动**：没有任何定时器/后台轮询去建库或更新。
2. **不由开关触发**：`enabled=true` 不产生任何请求。
3. **不由用户提问触发**：问一句不会拉起采集，也不会"顺手补一下缺失条目"。
4. **不让安装者重抓全站媒体**：库只存原文与媒体**引用**；图片按发送需要取。

**部署简化是未来对照实验**（13.4），不是本节的隐藏开关：实验未通过前，不存在"轻量模式下少抓"的分支。

### 7.3 进度告知

四路均启动时最多三条自动消息：

1. **受理**：「两榜和攻略源已开始更新；资料库在后台同步。」
2. **快报**：原三路结束即发各自结果，不等资料库。
3. **终报**：资料库成功 → 「新增／重抓／移除／复用」+ 发布时间；失败 → 失败阶段、已完成数、「旧库仍为上次发布版本」或「首次建库尚未完成」。

**不定时刷群进度。** 重复执行命令时，对在飞任务返回当前阶段与 `X/Y`，不启动第二份。详细进度写日志。

### 7.4 失败与断点

- 第 N 篇断网 → 当前批次失败，记录阶段、`content_id`、错误类型、成功数；**`last_verified` 不推进**
- 旧正式代继续按上次校验时间回答；没有旧库就显示首次建库失败
- **插件不排下一次恢复**（手动更新语义）
- staging 保留已校验条目，下次 `/st_update` 先重盘点，再按 `(content_id, 观测版本, parser_version)` 复用匹配记录
- **不按「第 N 篇」序号续跑**，**不把前 N 篇提前发布**

## 八、抓取节奏与时间

### 8.1 历史观测基线（不再是 SLA）

| 项 | 观测值 | 说明 |
|---|---|---|
| 一轮全量串行抓取（0.12s 间隔） | 4 分 33 秒，零失败 | **一次历史观测**，当轮清单规模见当轮记录 |
| 单篇网络耗时（均值） | 0.245s | 同上 |
| 单篇响应体积 | 10-156 KB | 同上 |
| 目录树 | 0.42s / 203 KB | 同上 |
| 清单分页 | `page_no` + `limit`，`page_total = ceil(total/limit)` | 结构性事实，仍成立 |

**「4 分 33 秒」只是那一次抓取的观测结果**：

- **不是安装 SLA**，不是对新用户的承诺，不是产品指标
- 不能按它推算"首次建库要几分钟"——规模、网络、上游状态都会变
- 本轮目录、清单及 722 篇详情共实测 **278 秒**（13.2.1）；同样不含图片下载或正式建库

**仍然成立的是节奏纪律**，不是速度承诺：

- 同一 GameKee API 主机：**最多 1 条在飞请求，串行，间隔 0.12 秒**（历史可行值）
- 0.12 秒**不是 GameKee 公布的配额**，不构成「反复全量抓取永远安全」的保证
- 观察到 429、验证页、连续 5xx → **按 2.3 停批并记录**，不自动加压/加压式重试

### 8.2 生产参数（结构固定，耗时在目标环境验收）

| 阶段 | 请求数 | 耗时 |
|---|---|---|
| 目录 + 清单盘点 | 约 9 | 按实测填，不预设 |
| 首次全量详情 | **= 待抓 K（运行时算）** | 研发采集实测见 13.2.1；生产建库耗时待测 |
| 后续增量（仅变化的） | 视上游 | 待实测 |

**不使用「1.25 秒/请求」推算值**（历史保守建议，从未实测全量）。

**边界**：0.12 秒证明的是「一次连续抓取可行」，不证明长期安全；GameKee 未公布配额，长期累积效应未知。**失败纪律优先于速度**（2.3）。

### 8.3 与现有 GameKee 探查的关系

现有 how 的后台探查（24h 周期、60s 启动延迟、30 分钟失败重试）**保持不动**。what 的抓取**只在 `/st_update` 时发生**，不参与自动调度，**不由 `[what] enabled` 开关触发，也不由用户提问触发**。

两者共用 `net_common.build_opener` 与请求预算；what 的长批在 `/st_update` 期间运行，**不与 how 的短探查争抢**（短探查优先）。

**部署简化是未来对照实验**（见 13.4）：实验通过前，本节合同不变——不存在"轻量模式下自动少抓"的隐藏分支。

## 八·五、顺带修复：how 成功回执引导不存在的工具

### 问题（实测确认）

`plugin.py` 有 **3 处**成功回执写着「请立即调用 stop 工具结束本轮」：

| 行 | 场景 |
|---|---|
| 1271 | GameKee 未找到攻略 |
| 1307 | 攻略图已发送（主路径） |
| 1323 | 猫猫球暂未收录 |

但宿主 1.4.8 的内置工具清单是：

```
wait, reply, schedule, query_memory, tool_search,
subagent, subagent_status, subagent_stop
```

**没有名为 `stop` 的工具。** `stop_after_execution=True` 本身已经完成终止，这句话是纯误导——模型可能因此产生一次无效调用，浪费一轮并可能踩到熔断。

### 修法

三处统一改为**不提任何工具名**的表述，只说明事实：

| 原 | 改为 |
|---|---|
| 「…请立即调用 stop 工具结束本轮。」 | 「…本轮无需再回复。」 |

`stop_after_execution=True` **保持不变**（用户裁决不动 how 的停轮行为，这里只改文案，不影响行为）。

### 为什么放在 1.5.3

- 改动 3 行字符串，无行为变化，风险为零
- 1.5.3 要新增 what 并复用 `_filter_planner_tools`，正好同批验收
- 不清掉它，what 上线后 how/what 混合提问场景会更容易踩到无效 `stop` 调用

### 验收

- 三处文案不含 `stop` 字样
- 现有 how 相关测试（节 G/K/S/T）不回归，PASS=245 保持
- 实机：查一个未收录角色，观察 planner 日志无 `stop` 调用尝试

### 10.2 标注集与对照（评测的唯一依据）

首次发布前建一份**人工标注集**，与样本同范围保留（不挑好样本）：

| 指标 | 说明 |
|---|---|
| 实体准确率 | 认对实体没 |
| 字段/条件准确率 | 认对字段没；描述题的对象/属性/槽位/条件是否同条命中 |

### 10.3 实机验收清单（QQ）

1. `[what] enabled = false` 时：planner 看不到工具、**零网络**、零后台任务
2. 打开 `enabled` 但**没建库**：返回"请执行 `/st_update`"，**不触发任何抓取**
3. `/st_update` 首次建库：三路报告先到，资料终报后到；全程群里可查旧资料
4. 断网中断后重跑：不复用错误断点、不提前发布、`last_verified` 未推进
5. 字段题：「优叶生日」「优叶90级攻击」「泡沫主位效果」「优叶几岁」（应明确答无年龄字段）
6. 同名消歧：「魔王」单独出现 → 分来源列候选，不静默挑一个
7. 描述题：「那个加地系伤害的秘纹」→ 只发同一条效果内匹配的候选，初筛假命中被剔除
8. 多候选：「塔8发育」命中多篇 → **全部合格候选一起发、来源分隔**
9. 媒体题：「魔王有立绘吗」→ 发已判定 `character_art`，`unknown` 不发
10. 无可提取文字页：「加载漫画是什么」→ 答"这是图片页"，**不假装读过图**
11. 未命中：查一个不存在条目 → **「没查到」+ 停轮**
12. 故障：模拟资料库读取失败 → **「读取失败」+ `success=False`**，不报成「没查到」
13. 部分交付：模拟部分已发、后续明确未发 → **「部分发出」+ 不设停轮**；日志或回执记录已发、未发及原因
14. 送达未知：模拟 `forward` 回执超时 → **「送达不确定」+ 不重发**
15. 混合提问：「优叶怎么玩，她生日几号」→ 记录实际行为（how 的停轮仍可能导致文字丢失，属已知边界）
16. 体积：大图集按**目标宿主版本上限**验证；需要分包时顺序完整，每个合并转发最后一行都是 `来源：https://www.gamekee.com/stellasora`，无默认截断（6.5）

**实机只在 QQ 上做**；`dev` 全量功能 + 用户实机通过后，才讨论 main / Release。

**必做的对照实验**（同一组标注集，同范围）：

| 对照项 | 要求 |
|---|---|

| 纯图 / 多候选 / 查不到 | 边界状态 |

**决策与保留**：

- **实验未通过** → 保留基线（全量本地库）继续发布与维护；**不影响已发版本**
- **实验通过** → 才讨论替换，且替换后仍要按阶段 2 的出口重新验收
- **无索引纯按需**只有在**上游定位覆盖验证**通过后才考虑。目前目录/标题/部分图鉴别名搜索**并未证明覆盖正文/效果**

- **不默认让安装者重抓全站媒体**

**部署简化是未来对照实验，不是当前实现项**：实验未通过前，2.3 / 7.2 / 8.3 的采集合同不变。

## 附录 B：调研方法与教训

### B.1 本轮调研的失误

**直到用户质疑「我们曾经网络搜索过方案吗」，整个方案讨论都没有做过业界对照。**

原因：给 planner 的第一封任务里写了「可以联网搜索」，但后续每一轮追问都写了「不需要再联网」「不要写完整计划文档」。结果方案只建立在本地实测 + 读宿主源码 + 推理上。

**教训**：多轮迭代里，早期的开放指令容易被后期的收敛指令覆盖掉，导致调研维度悄悄丢失。

### B.2 调研后实际改了什么

| 项 | 调研前 | 调研后 |
|---|---|---|
| 分词 | 空格切分 + unicode61 | `U+0001` 逐字（可逆预处理）+ 原文复核 |
| 假命中 | 未考虑 | **必须从 `body` 复核** |
| 小词表 | 建库时预切 | **查询侧扩展**（索引侧分词有损） |
| 向量库 | 曾考虑 | 明确不上（30 分） |
| journal | 未考虑 | 备库 `DELETE`（避开 WAL-reset） |
| 纯图判定 | 按 `word_count` | 按证据分级（文本/结构/媒体引用） |
| 时间估算 | 1.25s 间隔推算 15 分钟 | 0.12s 间隔的一次观测；**不再当 SLA** |
| 媒体去重 | 按 `image_num` 对齐 | 引用位置 / 唯一 URL / 字节 三层分离 |

### B.3 可复用的验证方法

1. **本地实测优先**：能在宿主环境跑的就跑，不靠文档推断
2. **对照实验**：同一语料、同一查询，比较多种方案的实际命中
3. **反例驱动**：主动找能推翻结论的样本（如 `728502` 的 1→7、`715315` 的 204→70）
4. **看源码不看营销页**：`dsh-chinese-search` 的 benchmark 源码推翻了它的宣传数据
5. **区分三类**：实测 / 来源 / 推断，**推断不能当结论写进设计**
6. **区分完成度**：详情+引用 / 字节下载 / 人工语义验收是三个不同层次，不互相冒充
7. **按版本核对常量**：宿主编译常量随版本变化（16 vs 32 MiB），不能跨版本套用
